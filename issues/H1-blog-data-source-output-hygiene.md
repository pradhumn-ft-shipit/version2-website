## Problem (verified)
`public/blog-data/posts/` is BOTH source and output:
- **196 legacy posts** exist ONLY as committed JSON (no markdown source) — genuine source-of-truth from the pre-markdown migration. Must not be lost.
- **75 redundant** committed JSON + **168 untracked** JSON are just rendered output of `content/**/*.md` (regenerated every build). They pollute the working tree (168 untracked) and drift (committed `index.json` lists 271 while disk has 439).

`build-blog-data.mjs` rebuilds `index.json` by scanning **all** JSON in `public/blog-data/posts/` (`readdirSync(POSTS_DIR)`), which is why legacy + rendered are tangled in one dir.

**Target invariant:** `content/` = the only tracked blog/news source. `public/blog-data/`, `public/news-data/`, `public/sitemap.xml` = 100% build output, git-ignored, regenerated by `npm run blog:build`. Nothing generated is ever committed again.

## Slice
- **New source dir (tracked):** create `content/legacy-posts/` and MOVE into it the legacy post JSON — i.e. every `public/blog-data/posts/<slug>.json` whose `<slug>` has NO corresponding markdown under `content/blog|tejas` (≈196 files). Detection:
  ```
  for f in public/blog-data/posts/*.json; do s=$(basename "$f" .json);
    find content -name "$s.md" | grep -q . || echo "$s"; done
  ```
- **Build script (`scripts/build-blog-data.mjs`):**
  - Before regenerating `index.json`, populate `POSTS_DIR` deterministically: clear it, render all markdown → JSON, then COPY every `content/legacy-posts/*.json` into `POSTS_DIR`. So the index scan still sees legacy + rendered — same output as today, but legacy now comes from a tracked source dir, not from committed output.
  - Add a `LEGACY_POSTS_DIR = content/legacy-posts` constant; read it alongside the markdown dirs.
  - Confirm the same for news if any news post is JSON-only (currently news is 1 post, 1 markdown source — no legacy news; just verify).
- **Untrack the generated artifacts** (keep on disk; build recreates them):
  - `git rm -r --cached public/blog-data public/news-data public/sitemap.xml`
  - (The 196 legacy are removed from the OLD path here too — they now live tracked under `content/legacy-posts/`.)
- **`.gitignore`** — add:
  ```
  public/blog-data/
  public/news-data/
  public/sitemap.xml
  ```
  Leave `public/blog-images/` TRACKED (out of scope — image sourcing is a separate story).
- **Delete lingering untracked output** then rebuild to prove regeneration:
  `rm -rf public/blog-data/posts public/news-data/posts public/blog-data/index.json public/news-data/index.json public/sitemap.xml && npm run blog:build`.

## Safety gate (do this, non-negotiable)
Before removing/ignoring anything, snapshot the current slug set:
```
node -e "console.log(require('./public/blog-data/index.json').posts.map(p=>p.slug).sort().join('\n'))" > /tmp/slugs-before.txt
```
After the rebuild, regenerate the same list into /tmp/slugs-after.txt and `diff` them.
**The diff MUST be empty** (identical slug set — none dropped, none duplicated). Detect
legacy by the post's **frontmatter slug**, not just filename, so a markdown post whose
slug ≠ filename is NOT mis-moved into legacy-posts (that would duplicate-slug the build).
If the diff is non-empty or `npm run blog:build` reports a duplicate slug, STOP and report.

## Notes
- Zero production impact: Render already regenerates all of `public/blog-data` at deploy (origin/main's `index.json` is a stale 271 — prod does NOT rely on committed JSON). This just makes the repo match that reality.
- Do NOT gitignore `public/blog-images/` — those aren't fully regenerable from tracked sources here; leave them as-is.
- Verify nothing reads `public/blog-data` as *source* outside the build: `scripts/prerender.mjs` and the client fetchers read the BUILT output (dist / post-build), and both run after `blog:build`, so ignoring the committed copies is safe.
- Relates to the standing rule: don't commit regenerated blog-data/blog-images/sitemap.xml. This ticket makes that rule structural instead of manual.
