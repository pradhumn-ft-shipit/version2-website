# FastTrackr AI — Marketing site

Vite + React 19 + React Router v7 (framework mode) + Tailwind. Static-site generation: `react-router build` runs every route at build time and serializes the full rendered `<body>` to HTML, so crawlers that don't execute JS see real content; the client bundle hydrates it and acts as an SPA for navigation.

**Hosting:** Render static site (`render.yaml`) serves the prerendered `./dist`. The only server-side piece is the contact form, which runs on a Cloudflare worker (`*.pages.dev/api/contact`) — the app calls it via `VITE_CONTACT_API_URL`. There is no Node/Workers runtime for the site itself.

## Common commands

- `npm run dev` — local dev (rebuilds blog data, then `vite`)
- `npm run build` — production build: `blog:build` → `tsc -b` → `react-router build` (prerenders every route) → `stage-dist` (copies `build/client` → `dist`)
- `npm run blog:build` — regenerate blog JSON only

## Where things live

- `app/routes/` — framework route modules; each wraps a `src/pages/` component and exports a `meta()` (per-page SEO via `seoMeta`) plus a loader for dynamic routes. The route tree is declared in `app/routes.ts`; `react-router.config.ts` enumerates what to prerender.
- `src/pages/` — the page components (`Home`, `Blog`, `BlogPost`, `Resources`, `Pricing`, `Contact`, ICP/solutions subfolders, etc.) rendered by the `app/routes/` modules.
- `src/components/` — shared sections (`Navbar`, `Footer`, `Hero`, `FAQ`, `PageCTA`, …) and `ui/` primitives.
- `src/lib/blog.ts` — client fetchers for the blog index and individual posts.
- `src/lib/blogCategories.ts` — canonical Resources-page categories. Source of truth for the `topic` values blogs can use.
- `content/blog/<slug>.md` — authoring source for new blog posts (Markdown + YAML frontmatter).
- `content/news/<slug>.md` — authoring source for press releases / announcements shown at `/resources/news`.
- `content/legacy-posts/<slug>.json` — the ~196 pre-markdown migrated blog posts that exist **only** as JSON (no markdown source). Tracked source-of-truth; the build copies these into `public/blog-data/posts/` alongside the markdown-rendered posts.
- `src/lib/news.ts` — client fetchers + types for the news index and articles.
- `src/lib/seo.ts` — `seoMeta(config)`: builds a route module's `meta()` output (title, meta description, canonical, OG/Twitter, JSON-LD) so the framework bakes it into the static `<head>` at build time. Plus `absoluteUrl`/`clampText` helpers.
- `scripts/build-blog-data.mjs` — clears `public/blog-data/posts/`, renders `content/blog/*.md` + `content/tejas/**/*.md` to JSON, copies `content/legacy-posts/*.json` in, then regenerates `public/blog-data/index.json` from every post JSON on disk.
- `public/blog-data/`, `public/news-data/`, `public/sitemap.xml` — **git-ignored build output**, 100% regenerated by `npm run blog:build`. Never commit these; the source of truth is `content/` (incl. `content/legacy-posts/`).
- `public/blog-images/` — committed blog imagery (TRACKED, not regenerable from tracked sources); reference as `/blog-images/<file>`.
- `render.yaml` — Render Blueprint: build command, env vars, and the live site's routing (301 redirects + clean-URL rewrites that map each prerendered route to its `dist/<route>/index.html`, ending in the SPA catch-all). **Source of truth for the deployed site's routing.** Note: Render Blueprint sync does NOT delete rules removed from this file — prune those by hand in the Render dashboard.
- `public/_redirects` — Cloudflare Pages redirects (SPA fallback + 301s), used only by the `*.pages.dev` worker deployment that hosts `/api/contact`.

## Blog workflow

Marketing drops a Markdown file into `content/blog/<slug>.md` (frontmatter + Markdown body); the build script renders it to `public/blog-data/posts/<slug>.json` and rebuilds `index.json`. Legacy migrated posts (JSON-only, no markdown) live tracked under `content/legacy-posts/` and are copied into the output on every build. `public/blog-data/` itself is git-ignored build output — regenerate with `npm run blog:build`, never commit it. Full marketing-facing guide: **`BLOGS.md`**. Deeper architecture notes (migration paths, GitHub/CI setup, redirects): **`Blog-Migration-Guide.md`**.

## News workflow

Drop a Markdown file into `content/news/<slug>.md`; the same build script renders it to `public/news-data/posts/<slug>.json`, rebuilds `public/news-data/index.json` (reverse-chronological), and adds `/resources/news/<slug>` to `sitemap.xml`. Validation is strict — a missing `title`/`date`/`description`/`excerpt`/`intro`, or a malformed `coverage` entry, fails the build. The frontmatter parser understands a deliberate subset of YAML: `key: value` on one line, and `- item` block lists at any indentation. Multi-line values (`intro: >` with the text on following lines) are **rejected with a build error** rather than silently truncated — keep each value on a single line.

Frontmatter fields: `slug`, `title` (the headline, rendered as the `<h1>`), `seoTitle` (optional, keep under 60 chars), `label` (e.g. `Press Release`), `date` (the original release date — drives sort order and `datePublished`), `description` (meta description, ~150–155 chars), `excerpt` (one line for the index card), `intro` (original FastTrackr framing shown above syndicated release text — this is what keeps the page non-duplicate), `image` + `imageAlt` (site-absolute path into `public/news-images/`), and `coverage:` as a block list of `Outlet Name | https://url` lines.

Images go in `public/news-images/` and are referenced as `/news-images/<file>`.

The Resources page (`src/pages/Resources.tsx`) auto-builds category sections from the blog index, grouping by the post's `Topic` field via `resolveCategoryId` in `src/lib/blogCategories.ts`. To change the category list or blurbs, edit that one file.
